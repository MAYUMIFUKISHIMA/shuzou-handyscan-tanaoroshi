# BT-W250 棚卸専用ハンディアプリV1

更新: 2026-11-01（日本時間）。開始時の共有main: `7fdfaa1ee4d39d7128f9834a9de57966518ae5d7`。

## 確定した方針

ユーザー報告では、Gakken既存アプリは実数0・予定超過数量を登録できない。このため棚卸専用アプリを開発する。既存アプリ・設定・現場データを上書きせず、メーカー対応方式を確認して検証用に導入する。

中継機器経由のFTP・共有フォルダー通信は既存アプリで動作確認済み。専用アプリにも同じ経路が使えるか、配置場所、利用権限、通信ソフトとの契約、認証の管理方法、転送途中ファイルの扱いは未確定。通信経路があることを、新規アプリから利用できる根拠にはしない。

本仕様は2026-11-01のユーザー引継ぎで承認・実装依頼済みの要件を正本として保存したもの。既存出荷検品アプリをそのまま採用しない。以下の承認済み要件を再承認待ちにはしない。OS/SDKや正式CSVなど技術・運用上の未確認事項は別途確認する。完成判定は `docs/release-acceptance.md` のD01〜D07/A01〜A08に従う。

## 現場試験の後半（ユーザー報告）

- 端末はKEYENCE BT-W250。既存Gakken i3 Handyで共有MSTからFTP投入、RESへの実績回収が成功。
- PC側中継機器はUSB Ethernet/RNDIS Gadgetとして認識。専用アプリからの利用可否は別確認。
- 修正版Code128ラベルで英数字商品コードを読取可能。旧HTMLのSVG切り抜きID重複が読取不良の原因で、mainの7fdfaa1で修正済み。
- 既存アプリは予定超過と数量0を拒否。欠品完了を有効にすると予定10・実数8を完了でき、実績8・不足2を回収。
- マルチ入力による1加算後、バラ8の手入力で累計9となる履歴を確認。既存アプリの加算挙動はV01/V03とは異なり、専用アプリへ引き継がない。

## 全体の工程

売りex CSV → PC対象取込 → 中継機器 → ハンディ計数 → PC実績回収 → 差異・未棚卸・競合確認 → 売りex用CSV → 反映照合。PC試作の成功だけで、実機/売りex往復の完成とはしない。

## 最小アプリの受入シナリオ

架空商品（先頭ゼロを含む）、基準10、棚位置A、担当者、端末IDを配布する。対象受信後に棚卸番号・配布版を照合し、商品読取で数量が変わらないこと、0/8/12の保存、8→7訂正、アプリ中断・再起動後の保持、PC回収と同一結果再送を順に確認する。未入力の商品を別に残し、ゼロとの区別を確認する。

保存失敗時の入力保持・成功非表示、PC保存後の応答消失、別端末の同一商品/棚位置の競合、既存出荷アプリ/既存MST・RESデータへの影響なしも必要条件。公式サンプルのビルドと実行を確認してから端末向けアダプターを実装する。現時点ではホスト上の業務/転送処理のみであり、この受入シナリオを実機合格とは記録しない。

ホスト試作の数量は既存契約の非負数値文字列（整数12桁、小数6桁以内）。これは本番の単位・入力上限の決定ではない。バーコードと商品番号の対応は仮データ上で一致させており、正式対応表を推測しない。

## 保存と転送

1. 読取後に商品と既存数量を表示する。読取だけで記録を作らない。
2. 明示した実数を新しい記録IDで保存する。同一商品・区画の前記録は履歴に残す。
3. 送信時は最大1000記録を順序付きのバッチとしてDBへ保存してから外部へ渡す。
4. PCの記録保存と受領応答保存を一括実行する。破損・古い配布版・ID衝突は拒否する。
5. 応答が届かなければ、端末再起動後も固定済みバッチを再送する。新しい訂正は先行バッチへ混ぜない。
6. 端末は保存済みバッチと受領のID・配布版・記録ID一覧が一致する場合のみ、受領状態を一括更新する。保存失敗時は全件未受領のまま再試行する。
7. 受領確認後に追加分の次バッチを作る。古い応答が遅れて再到着しても次のバッチを消さない。受領済み履歴も保持する。

SHA-256は内容の識別・破損検出であり、送信者の認証や悪意ある改ざんへの防御ではない。実転送の認証・権限は専用アプリの通信方式とともに確認する。

既存の模擬DBには `batches` テーブルを追加し、計数履歴を消さない。旧版で送信済みのバッチそのものは旧DBに保存されていないため、過去のバッチ境界を復元できるとは保証しない。未回収の旧版データは元の配布版・DBを保全してPCと照合し、正式な移行を確認する。実機の保存方式としてSQLiteを選定したものではない。

## 再現する

Python 3.12以上、外部Pythonパッケージ不要。リポジトリルートで実行する。

```sh
python -m unittest discover -s tests -p test_handheld.py -v
python -m inventory.handheld_demo --output data/dedicated-v1-demo-001
python -m unittest discover -s tests -v
node tests/test_client.cjs
```

デモの出力先は未使用のディレクトリを指定する。架空データだけを使い、実機への配置やFTP送信はしない。PC画面は `python -m inventory.server` でループバックに起動する。ブラウザ試験は `npm ci --ignore-scripts` 後、`CHROMIUM_PATH=/usr/bin/chromium npm run test:browser`（当クラウドの既存Chromium）を使用する。

## 実機開発に必要な次の情報

- OSは公式仕様でWindows Embedded Compact 7、SDKは公式案内でBT-WHD1同梱と確認済み（[調査記録](sdk-research.md)）。実機OS/ファーム版の照合、SDK版、ホストOS、IDE/ランタイム、ライセンス、配布条件は未確認。
- 公式サンプルのビルド環境とスキャナー・物理キー・日本語表示・永続保存API。
- 専用アプリが既存中継機器のFTP/共有フォルダーを利用する条件と、既存Gakkenとの共存・戻し手順。
- 実装時のキー割当、画面表示量、単位、未登録コードの扱いを既存設計と実機制約に照合する。承認済みV01〜V10は変更しない。

SDKが揃うまでは仮のDLL名やAndroid/Web対応を前提にした端末プロジェクトを作らない。現時点の成果物はPythonによるホスト模擬実装で、BT-W250用EXE/CAB/APKは未生成。実機の受入は `device-test-plan.md` に加え、基準10→実数12の保存・回収と、受領待ち中の訂正→再起動→順次再送を必須とする。
