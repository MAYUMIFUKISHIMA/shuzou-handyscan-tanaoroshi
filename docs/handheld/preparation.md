# BT-W250 実機なしでの開発準備

実機写真からの確定事項と次の確認は[写真の観察記録](observations.md)を参照する。既存Gakken i3 Handyの機能確認を、新規端末アプリ開発方式の確定に先行させる。

## 到達点

公式資料の調査を試み、PC上の模擬端末・論理転送形式・試験手順を作成した。BT-W250対応SDKの入手、端末向け方式の確定、端末実行ファイルのビルドは未完了。Python模擬端末をBT-W250へコピーして動作するという意味ではない。

## SDK入手・ビルドのチェックポイント

1. メーカー公式の機種対応資料を取得し、製品名・版・URL・確認日を記録する。
2. ダウンロード/利用/再配布の条件、購入・会員登録・契約の必要性を確認する。資格情報をGitやチャットへ書かない。
3. ライセンスを満たすWindows等の開発ホストに、公式インストーラーと対応IDE/ランタイムを用意する。インストーラーの署名や公式チェックサムを検証する。
4. SDK付属の最小サンプルを変更せずビルドし、ツール/SDK/ターゲットの組合せを確認する。
5. 読取、キー入力、日本語表示、ローカル保存、PC転送のアダプターを公式APIで実装する。模擬実装の状態と試験ケースを移植する。
6. 実際に成功したコマンドまたはIDE操作、設定、警告、生成物ハッシュをbuild-record.mdへ記録する。想像したDLL名やコンパイラ設定で動くプロジェクトを作らない。
7. スキャナーの代用入力を使う場合は模擬動作と明示する。SDKにシミュレーターがあるかも確認する。実機未検証のアプリは検証専用として配布する。

現環境はLinuxで、dotnetコマンドは見つからない。BT-W250の対応開発環境自体が未確認なので、単に最新版.NETを入れて端末向けビルドができるとは判断しない。現時点の成果物はホスト側Python実装と文書で、端末用EXE/APK/CAB等は生成していない。

## PC上の模擬端末を動かす

リポジトリルートでPython 3.12以上を使用する。

```sh
python -m inventory.handheld_demo --output data/handheld-demo-001
python -m unittest discover -s tests -p test_handheld.py -v
```

出力先は新規ディレクトリを指定する。既存データを上書きしない。架空資材のPC用DB・模擬端末DB・配布/送信/受領JSONを作る。保存→再起動→PC受信→受領応答消失→同じバッチ再送→受領確認を再現し、実数8・差異-2・重複記録なしを確認する。実機OSやスキャナーAPIのエミュレーターではない。

## 論理転送形式（試作schema=1）

- 配布: 棚卸ID、元CSVハッシュ、確定世代、商品、区画。正規化JSONのSHA-256をdistribution_idとする。
- 送信: 棚卸ID、distribution_id、最大1000件の計数記録。内容のSHA-256をbatch_idとする。
- 受領: batch_id、distribution_id、受信した記録ID一覧。PCはデータと受領結果を一括保存する。
- 端末は永続保存した記録を、受領内容が送信内容と一致した場合だけ受領済みにする。記録自体は削除しない。
- 端末未確認なら同じIDと内容で再送する。PC側は同じバッチの再処理を避ける。
- 配布世代が違う、内容が破損、別端末/棚卸の保存先を使う場合は拒否する。

これは内部の論理契約。正式な文字コード・通信媒体・端末ファイル形式ではない。模擬端末では未登録コードを拒否する。実機用の未登録保留、日本語画面、単位表示、端末記録日時、配布更新の受領手順はSDK確認後に追加する。数量・商品番号・受信原子性は既存PCモデルを再利用する。
