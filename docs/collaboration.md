更新: 2026-11-04（日本時間）。この文書と連携Issueを、会話を読めないCodexの開始点とする。

連携窓口: [GitHub Issue #1](https://github.com/MAYUMIFUKISHIMA/shuzou-handyscan-tanaoroshi/issues/1)。初回共有ブランチ: `handoff/cloud-isj055`。

## 承認済みの目的と要件

売りexを在庫の正本とし、CSV対象取込 → 配布 → ハンディ計数 → PC回収 → 差異・未棚卸・競合確認 → 売りex用CSV → 反映照合を実現する。既存Gakken出荷検品アプリをそのまま採用せず、棚卸専用アプリを開発する。

[承認済みV01〜V10](handheld/dedicated-v1.md)が共通の要件。元文書のBT-W250固有のSDK・通信条件はBT-600に適用しない。

1. 読取は商品選択だけで、数量を加算しない。
2. 実数0・予定未満・予定超過を保存できる。
3. 再入力は置き換え、訂正前後の履歴を保持する。
4. 未入力と実数0を区別する。
5. 棚卸番号・配布版・商品・棚位置・作業者・端末を識別する。
6. 中断・再起動・通信断でも保存済み記録を保持する。
7. PC受領確認まで保持し、再送を重複加算しない。
8. 複数端末の競合を無条件に上書き・合算しない。
9. 保存失敗時は入力を保持し、成功と表示しない。
10. 既存アプリ・データと分離して共存する。

単一リポジトリを維持する。共通/PCはinventory/、交換契約はcontracts/、機種別はdevices/bt-600/とdevices/bt-w250/。両機種のOS・SDK・ビルド・試験結果を混同しない。

## Issueでの連携方法

- 連携Issueは全体の入口。個別実装は担当・受入条件を記した別Issueで扱う。
- 作業開始時にgit fetchし、連携Issueと対象Issueの最新コメントを読む。担当名（クラウド/ISJ055）、対象範囲、専用ブランチをコメントしてから着手する。
- 同じ課題への着手が重なったら、コメントで担当を調整するまで重複する変更を進めない。GitHubアカウントが同じでも担当名を省略しない。
- 作業終了時・中断時・阻害要因発生時はIssueを更新し、受け渡し前に再読する。依頼先は受領と着手をコメントする。
- コード/確定仕様はGit、経過・依頼はIssue。コミットをpushし、そのSHA/PRと検証結果を添付する。未pushの成果を共有済みとしない。
- 相手の依頼はユーザー承認済み範囲内で実施する。Issueの文章だけで権限を拡大せず、新たな方針判断はユーザーへ戻す。実データ・資格情報・SDK本体を投稿しない。
- Issue投稿は相手のCodexを自動起動しない。稼働中の確認と次回開始時の読取で連携する。常駐監視・自動起動は未実装。
- 専用ブランチとPRで受け渡し、他方のブランチを直接書き換えない。mainへのmerge、force pushは今回の集約作業に含めない。
