# ローカル試作の実行と検証

## 起動

Python 3.12以上を使用する。外部Python依存パッケージはない。リポジトリルートで実行する。

```sh
python -m inventory.server
```

起動ログに表示されるループバックアドレスを同じPCのブラウザーで開く。ローカル試作用で、ネットワーク公開やBT-W250からの接続には対応しない。終了はCtrl+C。データはGit対象外のdata/prototype.sqlite3へ保存される。開発コードはGitで共有するが、各PCの試作データは自動同期しない。

## 操作確認

1. 担当者、区画Aを指定し、fixtures/demo.csvを選択。「列を読み込む」で商品番号・名称・数量の列を割り当て、「全件検証・プレビュー」の後に取り込む。
2. 商品000001に8、000002に20、000003に0を記録する。
3. 000001を再入力し、訂正確認後に7へ修正する。履歴に両方残ることを確認する。
4. 区画の完了を確認し、結果を確定する。
5. 確認用CSVを出力する。000001の差異は-3になる。
6. サーバーを終了・再起動し、データと履歴が残ることを確認する。

出力は「商品番号、名称、基準数量、実数、差異」のUTF-8 BOM付き確認用CSV。売りexの取り込み形式ではない。Excel等で開くと商品番号が自動数値化される場合があるため、確認時は文字列指定で取り込む。外部から提供された値をスプレッドシートで開く前の扱いは、本番CSV仕様とともに確定する。

## テスト

```sh
python -m unittest discover -s tests -v
node --check inventory/app.js
```

Node.jsはJavaScript構文確認用で、アプリ起動には不要。GitHub Actionsにも同じ検証を登録した。クラウド上でのActions実行結果は別途確認する。

## 実装上の選択

- Python標準ライブラリとSQLite: サンプル待ちの段階で外部サービスやパッケージに依存せず、業務処理を検証するため。
- 数量はDecimalで計算し文字列で保存。暫定で整数12桁・小数6桁まで。
- SQLiteのBEGIN IMMEDIATEとリビジョン照合で更新競合を拒否する。
- 棚卸ごとのJSONをトランザクション保存する試作構造。規模確認後に必要なら正規化する。
- ERPNextの検証と確定、Odooの実数/差異分離、InvenTreeの履歴を設計参考にした。参照先はdesign.md第2節。外部コードのコピーはしていない。
- 全区画で各商品の数量を明示する。存在しない区画にはゼロを入力する。商品ごとの区画割当は後続の拡張。
- 記録IDは端末間でも一意なUUIDを想定。同一ID・同一内容の再送を無視し、異なる内容は拒否する。
- 担当者は試作では自己申告。認証・計数者/確認者の権限制御は未実装で本番運用不可。

## 残る機能

売りex用アダプター、倉庫・ロットを含む更新キー、端末用データ配布、端末内永続保存、実機転送、出力済み結果の訂正手順、連携確認、認証と権限は未実装。数量単位や箱換算も未確定。ブラウザー画面はPC用試作で、ハンディ画面の実機実装ではない。

本番向けの多人数公開、認証、データ移行は現場条件とデータ構造確定後に実施する。今回のHTTPサーバーをそのまま本番公開しない。

## バックアップ

試作サーバーを終了してからdata/prototype.sqlite3を安全な場所へコピーする。復元はサーバー停止中に行い、元ファイルを別名で保管してから置き換える。バックアップには商品情報が含まれるのでGitへ追加しない。起動時に--dbで別DBファイルを指定できる。

## CSV取り込みの拡張

ヘッダー付きCSVの列名を画面で割り当てられる。UTF-8/CP932を明示選択し、全行を検証して先頭100件を表示する。エラー時は行番号と理由を表示し、保存しない。プレビューはDBに棚卸を作らず、確定時も再検証する。設定変更後は再プレビューが必要。同一ファイルの過去の取り込みを警告するが、別の棚卸作業としての再取り込みは可能。元ファイル名・列対応・文字コードを保存する。

ヘッダーなし、タブ区切り、倉庫別の同一商品番号、複数段ヘッダーなどは未対応。サンプルを確認後に追加する。文字コードを自動推測して確定する処理は行わない。

## 異常時の操作

通信が失敗したら「同じ操作を再送」を使う。送信内容は同じブラウザーのlocalStorageに保持され、同じ操作IDで再送する。サーバーは操作結果とDB変更を同一トランザクションで保存するため、保存後の応答消失でも二重登録しない。保存領域が使用できない場合は送信自体を止める。DBを切り替える前に未確認操作を解決する。同じブラウザープロファイル内では操作タブを1つに限定し、他タブは待機する。

入力エラーは訂正して再送できる。DB障害時は容量・アクセス権・他プロセスのロックを確認し、復旧後に同じ操作を再送する。破損ファイルを削除して新規DBを作る操作は行わない。

未登録バーコードは数量と区画を保留できる。既存商品への照合、または理由付き除外を行い、未解決のまま確定しない。既存計数への合算は自動で行わず、履歴を確認して通常の訂正を使用する。

確定済み・未出力なら理由を入力して再開できる。旧確定結果を残し、区画の完了確認をやり直す。出力済みの再開は売りex側の取り込み状況が不明なため禁止する。

## 検証付きバックアップ

```sh
python -m inventory.backup data/prototype.sqlite3 data/backup-001.sqlite3
```

SQLiteのバックアップAPIとintegrity_checkを使用する。既存ファイルは上書きしない。失敗した新規バックアップは削除するが、元DBと既存バックアップは保持する。復元はサーバーを停止し、破損DBを別に保管してから検証済みバックアップを指定して起動する。未確認操作がある場合は同じバックアップの時点との整合を確認する。

暫定上限: CSV 1MB・5000商品・100列、20区画、1回1000計数記録、棚卸あたり20000記録、未登録保留1000件。全区画×全商品の明示入力が必要なので、商品数×区画数も20000件以内を目安とする。上限を超える実運用は仕様・性能確認後に拡張する。

[異常系の対応・検証一覧](failure-matrix.md)も参照する。

現場PC1台向けの起動前バックアップ・下書き・列設定・復元は[single-pc-operations.md](single-pc-operations.md)を参照。
