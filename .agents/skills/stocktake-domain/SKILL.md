# stocktake-domain

## 使用する場面

棚卸モデル、状態遷移、集計、訂正、複数端末処理の設計・変更時。

## 前提

リポジトリルートのAGENTS.md、docs/status.md、docs/design.mdを読む。業務仕様の正本はdocs/design.mdとし、食い違いがあれば根拠を確認して整合させる。既存チェックアウトを利用し、実データや秘密情報はコミットしない。

## 手順

1. docs/design.mdの第2・4・6・7節を読み、関連するERPNext、Odoo、InvenTreeの既存処理を確認する。参照したURLと版、採用理由を記録する。
2. 売りexの基準数量、計数記録、確定結果を分離する。取り込み後の基準数量を上書きしない。
3. 未棚卸とゼロを分離し、区画ごとの採用記録から実数を集計する。同一区画の訂正を加算しない。
4. 訂正元を残し、同一区画の複数端末による競合を自動上書きしない。解決前の確定を拒否する。
5. 端末IDと記録IDで再送を検知する。同じIDで内容が異なる場合はエラーとし、受信バッチを一括反映する。
6. 状態遷移と権限を明示し、確定結果を不変の版として保存する。CSV出力と売りex連携確認を分ける。
7. inventory-testingで集計、訂正、重複、競合、確定前提条件を検証する。

## 完了条件

設計の不変条件と状態遷移を満たし、集計・訂正・再送・競合の期待結果が検証されている。仕様変更は設計書にも反映する。

成果・検証結果・未確認事項・次の作業をdocs/status.mdに記録する。別端末で再現できる手順を残す。
