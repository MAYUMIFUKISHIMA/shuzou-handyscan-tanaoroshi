# inventory-testing

## 使用する場面

実装・修正の検証、受入テスト、端末やCSVの連携確認時。

## 前提

リポジトリルートのAGENTS.md、docs/status.md、docs/design.mdを読む。業務仕様の正本はdocs/design.mdとし、食い違いがあれば根拠を確認して整合させる。既存チェックアウトを利用し、実データや秘密情報はコミットしない。

## 手順

1. docs/design.md第10節と変更対象を照合し、必要なテストを選ぶ。実装の内部構造ではなく期待する業務結果を検証する。
2. 架空データを使用し、先頭ゼロ、未棚卸、ゼロ、基準10に実数8、同一区画の8から7への訂正、別区画3と5を含める。
3. 同一記録再送、同一IDの異なる内容、複数端末競合、不正CSVを検証する。件数と数量、履歴、状態を確認する。
4. 対象変更に応じて保存中断、再起動、転送中断、確定後の変更、出力後の連携失敗を検証する。
5. 業務処理の自動テスト、CSVの往復テスト、実機試験、売りex取り込み試験を分ける。モック成功を実機成功として扱わない。
6. 実行コマンド、対象版、期待値、結果、失敗理由を記録する。合格、失敗、スキップ、未実行、ゼロ件実行を区別する。
7. 実装不具合と環境不足を切り分ける。検証を通すために期待値を弱めず、必要な修正後に該当テストを再実行する。

## 完了条件

変更に必要な試験の結果と残る制約が記録されている。実機や売りexがない場合、その受入確認は未完了とする。

成果・検証結果・未確認事項・次の作業をdocs/status.mdに記録する。別端末で再現できる手順を残す。
